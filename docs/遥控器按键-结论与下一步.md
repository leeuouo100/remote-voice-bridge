# 遥控器按键：结论与下一步

> 生成：2026-09-23 凌晨（**第三次修订：第一次的"配对没密钥"是错的已推翻；今天上午的实测结果已并入**）
> 对应版本：v1.0.15 ｜ 面向：武哥。看这一页就够了，不用翻 CHANGELOG。

## 一句话

**蓝牙这一层完全健康。** 配对密钥齐全、Windows 正连着遥控器、驱动和 5 路 HID
集合都在 —— 所以"配对坏了 / 没有密钥"那条路**已经排除**。

**现在只剩一个问题**：按下去那一刻，那份按键报告到底**发不发**、发在**哪一层**。

## 先认账：昨晚那个"根因"是我判错的

| 昨晚我写的 | 今天实测 |
|---|---|
| "配对记录里一个密钥值都没有 ⇒ 链路加不了密 ⇒ 物理上不可能" | ❌ **错** |

错在哪：我去读的是 `BTHPORT\Parameters\Devices\<遥控器>`，那是**元数据**键
（名字、VID/PID、外观、时间戳）—— **它本来就不该有密钥**。
在那里找不到 LTK 是**正常状态**，不是异常。

真正的密钥一直都在，就在**以适配器地址命名的子键**里：

```
BTHPORT\Parameters\Keys\047f0ef2d294\f196a263671c\
    ✅ LTK  IRK  CSRK  EDIV  ERand  KeyLength  Address  AddressType
```

而父键 `Parameters\Keys` **确实**只放 SYSTEM（非管理员一律拒绝访问）——
**我在第一个挡路的地方就停了，没往下钻一层。** 这是这次真正该记住的教训：
**"读不到"必须追到"是哪一层读不到"，不能在第一个被拒的地方下结论。**

> 顺带查出这个错误**有源头**：`pairing.py` 里的 `read_key_material()` 以前
> 就是"先打开父键，打不开就直接返回"，所以它一直报"读不到密钥（权限不足）"，
> 甚至会**据此建议你重新配对**。工具先踩、我跟着踩。**这次两边都修了。**

## 今天（09-23 08:53）那次实测：结果与它排掉了什么

先说清楚要测什么。一份按键报告有**五种命运**，所以监听必须同时挂在三层上：

| 集合 | Windows 怎么处理 | 谁看得见 |
|---|---|---|
| Col01 键盘 | 当键盘事件 | ✅ 键盘钩子 |
| Col02 消费类 | 当媒体键 | ✅ 键盘钩子 |
| Col03 鼠标 | 当鼠标 | ⚠ 只有鼠标钩子（键盘钩子看不见） |
| Col04 厂商 `0xFF01` | **什么都不做** | 只有我们自己读原始报告流 |
| Col05 厂商 `0xFF80` | **什么都不做** | 只有我们自己读原始报告流 |

你按了，报告拿到了。**它排掉了一批可能，也暴露了我报告里的一个缺陷。**

| 通道 | 结果 | 能不能作证 |
|---|---|---|
| ATVV 语音通道 | **收到 4 条**（两次「按下-松开」：`audio_start`/`audio_stop`） | ✅ 证明遥控器**连着、在工作、你确实按了键** |
| 键盘钩子（真实按键） | 0 | ✅ 这是"Windows 有没有把它当键盘"的判据 |
| 消费类页 `0x000C` | 0 —— **这一路我们打开了、真观测了** | ✅ 真 0 |
| 厂商页 `0xFF01` / `0xFF80` | 0 —— **两路都打开了、真观测了** | ✅ 真 0 |
| 私有服务 `ae42` / `d343bfc5` | 0（都订阅上了） | ✅ 真 0 |
| 键盘页 `0x0001/0x0006` | 我们打不开（Windows 的 `kbdhid` 独占 —— **正常**） | ⚪ 由键盘钩子覆盖 |
| 鼠标页 `0x0001/0x0002` | 我们打不开 | ❌ **这一路根本没测** |

**顺手补测的三条（全是只读）：**

- 密钥材料**齐全**（`LTK/IRK/CSRK/EDIV/ERand/KeyLength/Address/AddressType`）；
- 链路参数是 **7.5–15 ms、零延迟**的 HID 档位（Windows 只对**活跃输入设备**这么配）；
- 遥控器**电量 88%** —— 不是没电。

⇒ **结论**：遥控器的按键报告，在**所有能观测到的页**上是**一条都没有**。
（"厂商页没被占用"这件事今天被实测作死了 —— 我们自己读得到，它没发。）

> ⚠ 这是**我报告的一个缺陷**，已经修了：原来那张表把"打不开、等于没观测到"也打成
> `0`，看上去像"这一路没有报告"。**读不到 ≠ 没有** —— 这条铁律我这一轮刚踩过一次，
> 不该在报告里再犯一次。

## 最像的那条机制：HID Control Point 被写成了 Suspend

HOGP 规范里有一个专门的状态：host 往 `HID Control Point (0x2A4C)` 写
`0x00 = Suspend`，**设备就立即停止发送输入报告**；要写 `0x01 = Exit Suspend` 才恢复。
我们现在这个现象 —— **连得上、参数正常、但一条输入报告都没有** —— 正好是它的样子。

**这一条我没能直接验证**（写那个特征同样被 `ACCESS_DENIED` 挡住，因为 HOGP 占着服务），
所以它是"最像"，**不是"已确认"**。但它给出了一条明确的处置顺序。

## 接下来做这两步（按顺序，别跳）

**① 先重启一次电脑**（1 分钟，零风险）

挂起状态是**跟着连接走**的 —— 断开重连会把这条状态清掉；重启同时会把 Windows 的
HOGP 那一层重新拉起来（它现在占着 `0x1812` 却一条报告都不送，本身就不正常）。

重启后等遥控器重新连上，双击 **`测遥控器按键通道.bat`**。
**不用记顺序** —— 它会分四段、每段只让你按一个键（确认 → 返回 → 主页 → 方向/音量），
并在屏幕上直接提示「现在只按【确认 OK】」。按它说的做就行。

> ⚠ 上一版的说明是"依次按每个键"，结果 08:53 那份报告里**唯一能证明你按过键的证据
> 只有两条语音键**，确认/返回/主页有没有按过根本看不出来 —— 于是"0 条"就有两种读法。
> 现在改成一段一个键、提示带秒数，报告里的事件行和提示行能直接对上号。

**② 还是不行，就重新配对**（这类毛病的标准解；也是唯一能重做"密钥协商 + 服务订阅"的动作）

1. 遥控器上**同时按住「返回」+「主页」约 3 秒**，底部指示灯开始闪 = 进配对模式；
2. Windows：设置 → 蓝牙和其他设备 → **删除**旧的「Chromecast Remote」→ 添加设备 → 蓝牙；
3. 连上之后**必须再跑一次 `修复蓝牙配对.bat`** —— 重配会换掉设备地址，
   不跑这一步语音会连不上（它把配对记录接管到新地址下，**不用你再配对一次**）；
4. 最后再跑一次 `测遥控器按键通道.bat`，按那三个键。

> ⚠ `tools\takeover_hid_reports.py`（把 Windows 的 HOGP 节点停掉、我们自己订 `0x1812`）
> **这条路已经作废**：09-22 真机实测 `Disable-PnpDevice` 回「不支持」、
> `pnputil` 回「Cannot disable critical system device」，那个节点的 `DevNodeStatus`
> 里**没有 `DN_DISABLEABLE` 位**（`0x0180000A`，设备管理器里"禁用"是灰的）。
> 不是我们没测成，是 **Windows 不许任何人让它放手**。别再去跑它了。
> 还剩下的那条 —— 鼠标页看不见、以及"没人订阅所以设备不发" —— 这两条
> **从用户态分不开**，只能靠上面①②去改变状态。

## 这一版（v1.0.15）顺手修掉的

1. **语音"按一次掉"修回**（v1.0.14 的回声窗口量错了：实测回声延迟最大 1070ms，
   而窗口只有 0.8s）。现在改成"欠账模型"，窗口 1.5s 且只靠时间过期。
   **这一条是真机上立刻能感觉到的。**
2. **三个永远不会命中的键名**（含 `escape` —— 库只会报 `esc`，
   所以"返回键"这条映射**从一开始就是死的**）。
3. **一个自激隐患**：默认把静音键指向 `mute`，而我们自己注入的 0xAD
   在钩子里被报成 `volume mute` —— 按键一旦真通就会无限自触发。已修（27 例全过）。
4. **`pairing.py` 那个"永远报读不到密钥"的 bug**（就是上面那个源头），
   顺带紧了它的判据：不许再拿"没找到"当"没有"去建议你重新配对。
5. 给"死键名"和"判词"都上了闸：CI 每次都会拿真实键名清单核对 `KEY_MAP`，
   并验证体检工具的判词**四种输入必须四种结论**（防止哪天被改坏还打 ✅）。
