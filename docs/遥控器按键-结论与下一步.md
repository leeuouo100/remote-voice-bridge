# 遥控器按键：结论与下一步

> 生成：2026-09-23 凌晨（**当天第二次修订 —— 第一次的结论是错的，已推翻**）
> 对应版本：v1.0.15 ｜ 面向：武哥。看这一页就够了，不用翻 CHANGELOG。

## 一句话

**蓝牙这一层完全健康。** 配对密钥齐全、Windows 正连着遥控器、驱动和 5 路 HID
集合都在 —— 所以"配对坏了 / 没有密钥"那条路**已经排除**。

**现在只剩一个问题**：按下去那一刻，那份按键报告到底**发不发**、发在**哪一层**。

## 先认账：昨晚那个"根因"是我判错的

| 昨晚我写的 | 今天实测 |
|---|---|
| "配对记录里一个密钥值都没有 ⇒ 链路加不了密 ⇒ 物理上不可能" | ❌ **错** |

错在哪：我去读的是 `BTHPORT\Parameters\Devices\<遥控器>`，那是**元数据**键
（名字、VID/PID、外观、时间戳）—— **它本来就不该有密钥**。
在那里找不到 LTK 是**正常状态**，不是异常。

真正的密钥一直都在，就在**以适配器地址命名的子键**里：

```
BTHPORT\Parameters\Keys\047f0ef2d294\f196a263671c\
    ✅ LTK  IRK  CSRK  EDIV  ERand  KeyLength  Address  AddressType
```

而父键 `Parameters\Keys` **确实**只放 SYSTEM（非管理员一律拒绝访问）——
**我在第一个挡路的地方就停了，没往下钻一层。** 这是这次真正该记住的教训：
**"读不到"必须追到"是哪一层读不到"，不能在第一个被拒的地方下结论。**

> 顺带查出这个错误**有源头**：`pairing.py` 里的 `read_key_material()` 以前
> 就是"先打开父键，打不开就直接返回"，所以它一直报"读不到密钥（权限不足）"，
> 甚至会**据此建议你重新配对**。工具先踩、我跟着踩。**这次两边都修了。**

## 现在确证的事（每条都有测量方式）

| # | 事实 | 怎么测的 |
|---|---|---|
| 1 | 密钥**齐全**：`LTK/IRK/CSRK/EDIV/ERand/KeyLength/Address/AddressType` 都在 | `python tools\probe_hogp_state.py` |
| 2 | Windows **正连着**遥控器（`ConnectionStatus = Connected`） | 同上（WinRT） |
| 3 | 8 个服务节点**都在场已启动**，`mshidumdf` 绑着，5 路 HID 集合都在 | 同上（cfgmgr32） |
| 4 | 键盘钩子**从来没**见过遥控器独有的键名 | 日志 + `probe_remote_keys_reach.py` |

## 剩下唯一的缺口：键盘钩子有"看不见的地方"

`hidwatch.py` 开头就写着这五种命运 —— 而**键盘钩子只看得见前两种**：

| 集合 | Windows 怎么处理 | 键盘钩子看得到吗 |
|---|---|---|
| Col01 键盘 | 当键盘事件 | ✅ 看得到 |
| Col02 消费类 | 当媒体键 | ✅ 看得到 |
| Col03 鼠标 | 当鼠标 | ❌ **看不到** |
| Col04 厂商 `0xFF01` | **什么都不做** | ❌ **看不到** |
| Col05 厂商 `0xFF80` | **什么都不做** | ❌ **看不到** |

⇒ **"按键报告其实来了、只是落在厂商页"这一支，从来没被排除过。**
而这一支是**纯软件能修**的：那一份报告我们可以自己去读、自己映射成按键，
**根本不需要重新配对**。

一次按键就能把答案逼出来 —— 因为监听会**同时挂在三层**上：
键盘钩子 + 鼠标钩子 + 5 路原始报告流。

## 你要做的（1 次按键，几分钟）

双击仓库里的 **`测遥控器按键通道.bat`**。它会：

1. 发现桥程序在跑 → 问你要不要替你退出（**选 Y**，不退出就听不全）；
2. 给出 3-2-1 倒计时，**倒计时结束再开始按**；
3. 依次按：**方向上下左右 → 确认 → 返回 → 主页**（手别碰键盘）；
4. 结束后报告落在 `%APPDATA%\remote-voice-bridge\watch-all-channels.txt`。

> 不想用批处理也可以，一条命令：
> `python tools\watch_all_channels.py --seconds 90`

## 报告怎么看（结论就这四种）

| 按键出现在 | 含义 | 修法 |
|---|---|---|
| **键盘层** | 报告到了 Windows，也翻成键盘事件了 | 问题在我们这层的映射/注入 → **纯软件能修** |
| **厂商页** | 报告到了，但 Windows 不翻译 | **自己读报告** → 纯软件能修 |
| **鼠标层** | 报告到了，Windows 当鼠标处理 | 要另外处理（也不难） |
| **哪层都没有** | 报告根本没来 | 才轮到下面两步 |

## 如果哪层都没有（才走这两步）

```bat
:: ① 只读体检：不改任何东西，先看它怎么说
python tools\takeover_hid_reports.py

:: ② 确认要试再执行（需管理员；非破坏性：临时停掉 HOGP 节点，然后自己订 0x1812）
python tools\takeover_hid_reports.py --go --seconds 25
```

它能把「**遥控器到底发不发按键报告**」一次说死：收到报告 ⇒ 我们能自己解码；
一条都没有 ⇒ 软件层到头了，那就只剩**重新配对**（遥控器同时按住
**「返回」+「主页」约 3 秒**，底部指示灯开始闪 = 进配对模式；Windows 先删掉旧的
「Chromecast Remote」再"添加设备 → 蓝牙"）。

> ⚠ 重新配对会换掉设备地址，语音那边可能要走一次配对接管，先记着。

## 这一版（v1.0.15）顺手修掉的

1. **语音"按一次掉"修回**（v1.0.14 的回声窗口量错了：实测回声延迟最大 1070ms，
   而窗口只有 0.8s）。现在改成"欠账模型"，窗口 1.5s 且只靠时间过期。
   **这一条是真机上立刻能感觉到的。**
2. **三个永远不会命中的键名**（含 `escape` —— 库只会报 `esc`，
   所以"返回键"这条映射**从一开始就是死的**）。
3. **一个自激隐患**：默认把静音键指向 `mute`，而我们自己注入的 0xAD
   在钩子里被报成 `volume mute` —— 按键一旦真通就会无限自触发。已修（27 例全过）。
4. **`pairing.py` 那个"永远报读不到密钥"的 bug**（就是上面那个源头），
   顺带紧了它的判据：不许再拿"没找到"当"没有"去建议你重新配对。
5. 给"死键名"和"判词"都上了闸：CI 每次都会拿真实键名清单核对 `KEY_MAP`，
   并验证体检工具的判词**四种输入必须四种结论**（防止哪天被改坏还打 ✅）。
